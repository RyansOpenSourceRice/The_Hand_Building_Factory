# Design

Why HANDS ON! is built the way it is.

## The game

You stand on a theater stage at a workbench. Parts of a robotic hand arrive in
front of you. You grab each part and slot it into a glowing outline. The crowd
cheers as the hand comes together. When the hand is complete, it celebrates,
and a new round begins with more parts.

The loop is deliberately simple: reach, grab, place, screw, cheer. It fits
the Meta Quest 3 comfort envelope (2-7 ft reach); movement exists only as a
small clamped fallback, and the experience works standing or seated.

## Platform

Quest 3 inside the Quest browser, hosted on itch.io as a browser-playable
game. There is no desktop or native build target for this jam. A desktop
preview still runs in any browser so the scene can be developed and tested
without a headset; the VR path is the product.

This project targets only the Quest 3 for the jam, which overrides the general
preference to ship VR plus web plus native from one codebase (§32). The
override is Ryan's live decision, recorded here.

## Lessons applied

A previous jam project failed because the headset was only tested at the end,
and because placeholder-quality assets were never replaced. This project:

1. Ships a running, interactive scene in the first milestone and tests it on
   the actual Quest 3 before any real assets exist.
2. Replaces placeholder geometry only once the core interaction is proven, and
   explores modeling techniques (with a timeboxed Blender-on-Qubes test and a
   guaranteed in-engine fallback) before committing to a pipeline.

## Asset policy

No third-party assets by default. Everything on screen is generated by code in
this repository. Two exceptions, both approved by Ryan:

- The Atkinson Hyperlegible font for UI text (accessibility).
- The yeah-hand STL-derived meshes for the hand parts, scaled 3x and
  placed in one shared assembly frame so palm, fingers, thumb, and cover
  form a connected hand. The palm faces the player, the servos stay
  visible on the back until the cover goes on, and metal uses the
  bare-steel tile. Imported under CERN-OHL-S-2.0 with credit.

The crowd, stage, and lighting are procedural and stay procedural. The crowd
is twelve golden-yellow mannequins in blue hard hats, seated on grey chairs in
two tiered rows of six facing the player, so the performer reads as the one
being watched. Instanced geometry keeps the room light; the small crowd is a
deliberate choice to protect the Quest frame budget.

Guidance is diegetic: a small status board above the hand stand, bobbing
yellow arrows on the part and its destination (always drawn on top), a soft
glow on the host while a part is waiting, and a grouped narrator that names
the host at each step.
The controller hands are five-digit box hands wrapped around the grip, so the
tool and the hand agree with the hardware the player is holding without
pretending to be a photoreal hand.

Surfaces use twelve seamless 256x256 tiles generated in code by
`scripts/gen-tiles.mjs`. Each material wraps the tile with its own UV scale,
mipmaps, and anisotropic filtering. This keeps the tile library near 6 MB
instead of a large atlas, and the procedural PLA layer tile gives printed
parts a filament texture that can be tinted by the palette.

## Structure decisions

- `src/` is TypeScript only; Vite is the bundler; there is no DOM framework
  because the entire interface lives inside the Babylon canvas. This is a
  documented deviation from the React default (§9): a pure-canvas game gains
  nothing from a virtual DOM and pays frame-time for it.
- The snap mechanic (check distance to a target, lock on success) is a pure
  service with no rendering dependencies so it can be unit tested headlessly
  with Babylon's NullEngine.
- Root file count exceeds the 8-file budget because the Vite/TypeScript/npm
  toolchain requires its config files at the root; all authored documentation
  beyond README/CHANGELOG/AGENTS/LICENSE lives in `docs/` to keep the root as
  close to the budget as the toolchain allows.
- Repo hosting is GitHub (Ryan's live decision), overriding the general
  "software packages to GitLab" routing (§27), because the jam repo already
  exists there and GitHub Pages provides the HTTPS staging URL needed to test
  WebXR on the Quest before the itch upload.
